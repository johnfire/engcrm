# Design: German + English UI support (web + Android)

**Status:** approved, implementing · **Date:** 2026-07-21

## Goal

Translate the app's own interface — nav, buttons, labels, screen content — into
German and English, on both the web app and the Android app. Explicitly **not**
about the existing `contacts.preferred_language` / outreach-drafting language
system, which already handles the business's language independently and is
unaffected by this work.

## Requirements (from discovery)

- Covers both web and Android, full coverage in one pass (all ~20 web
  templates, all ~22 mobile screens) — not a partial/incremental rollout.
- Language choice is a **per-account** setting, not per-device — set once,
  applies everywhere the account is signed in.
- Default for existing accounts and new invites: **English** (no surprise
  change for anyone on rollout).
- Mobile sync must be close to real-time: this is a commercial app, so
  "eventually consistent on next login" isn't acceptable.
- Translations are written directly (no separate human-review gate before
  shipping); issues get fixed after the fact if any read wrong.

## Architecture

### Data model

- `users.ui_language VARCHAR(5) NOT NULL DEFAULT 'en' CHECK (ui_language IN ('en','de'))`
- `push_tokens.user_id INTEGER REFERENCES users(id)` — push tokens weren't
  previously tied to an account (`send_push_to_all` broadcasts to every
  device, by design, for team-wide lead notifications). Needed so a
  language-change push reaches only that account's own devices.

### Web (Jinja2, session-based auth)

- `POST /settings/language` (session-auth, mirrors `/settings/password`)
  updates the DB and the live session — takes effect on the very next render.
- Pre-login pages (login, forgot-password, Impressum) get a simple toggle
  that sets `session['ui_language']` without needing an account yet. On
  successful login, the account's DB value overwrites the session and
  becomes authoritative from then on.
- `t(key, **params)` is injected as a Jinja global per-request inside the
  existing `AppTemplates.TemplateResponse` override (`gcrm/api/templates.py`)
  — it already has `request` in scope there, so no route handler needs to
  remember to pass anything.

### Mobile (Expo/React Native, JWT auth)

- `GET /api/auth/me` (new) → `{email, role, ui_language}`, called at cold
  start.
- `PATCH /api/account/language` (new) updates the DB, then sends a **silent**
  push (`send_push_to_user`, no visible banner) so other signed-in devices
  for the same account refresh immediately.
- An `AppState` listener re-fetches `/api/auth/me` on every foreground
  transition — covers a backgrounded device without needing push.
- A handler for the silent-push data payload re-fetches and re-applies —
  covers a device that stays foregrounded the whole time.
- Net effect: the device making the change applies it instantly (it already
  knows the new value); every other device applies it within about a second
  (push) or on next foreground (fallback) — no restart required either way.

### Translation files

- Two separate directories, no cross-project sharing:
  `gcrm/i18n/{en,de}.json` (web), `engcrm-mobile/i18n/{en,de}.json` (mobile).
- Flat, dot-namespaced keys mirroring screen structure: `nav.contacts`,
  `login.title`, `settings.logout`, `captureSign.hint`, etc.
- Interpolation: `{{var}}` substitution.
- Pluralization: i18next-style `_one`/`_other` suffixes, picked by a `count`
  param.
- Fallback: missing key in active language → English → still missing →
  visible `[missing.key]` marker (never silently blank).
- **The English value for every key is the exact existing hardcoded string,
  word-for-word.** This means every existing test asserting on rendered
  English text keeps passing unchanged — English behavior doesn't actually
  change, so it's a free regression net. German is the only genuinely new
  surface needing new test coverage.

## Rejected alternatives

- **gettext/.po files (web) + i18next (mobile):** industry-standard, but two
  new dependencies and meaningfully more machinery (compilation step,
  namespace loading, Suspense integration) than a static 2-language,
  ~200-key dictionary needs. This codebase consistently favors small
  hand-rolled utilities over frameworks for exactly this kind of scope.
- **Broadcast-to-everyone instead of per-user push targeting:** simpler (no
  schema change), harmless at today's ~4 accounts, but a real design smell
  for a commercial app with a growing user base — every user's device would
  re-check its language on every other user's change.
- **Auto-detect device/browser locale only, no manual override:** simplest
  to build, rejected because there'd be no way to correct a wrong guess and
  it doesn't satisfy "per-account, syncs across devices."

## Build order

1. Migration + `t()`/translation infra + new endpoints (`/api/auth/me`,
   `PATCH /api/account/language`, `POST /settings/language`,
   `send_push_to_user`) — nothing else works without this.
2. Settings language picker on both platforms — gives a way to test
   switching before every screen is converted.
3. Web templates (all 20).
4. Mobile screens (all 22) + the `I18nContext`/`useTranslation` hook,
   foreground listener, silent-push handler.

## Testing

- New: the `t()`/translation machinery itself on each platform (key
  resolution, interpolation, pluralization, English/bracket fallback), plus
  the new endpoints (including server-side rejection of an invalid language
  value).
- Not written: bespoke "is this specific string in German" tests per
  screen/template — low value, brittle; the shared-machinery tests prove the
  mechanism works everywhere it's used, and the English-string-preservation
  rule above already guards every existing test.

## Delivery

Several logical commits (migration+infra+endpoints, web templates, mobile
screens+tests) rather than one giant commit, for reviewability. Held locally
unpushed per current standing instruction until told to push.
