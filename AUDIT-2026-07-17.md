## 2. Open findings

### B1 — BUG: `NameError` in MCP server exception handlers
**Where:** `gcrm/mcp/server.py:430` and `:464` (in `run_research` and `trigger_run`)
**What:** both `except Exception as error:` blocks return `json.dumps({"error": str(e)})` —
`e` is undefined, so any failure raises `NameError` inside the handler instead of returning
the error message to the MCP client.
**Severity:** low impact, trivial fix, zero risk.

### S1 — MEDIUM (carried over): inbound email sender is unauthenticated; spoofed From still drives autonomous state changes
**Where:** `gcrm/tools/email.py` (`read_inbox` / `_parse_message`), `agents/gcrm-followup-agent/gcrm_followup_agent/graph.py:30-64, 223-251, 312`
**What:** the 06-24 review recommended gating autonomous actions on SPF/DKIM/DMARC
(`Authentication-Results` header). Not implemented — grep for spf/dkim/dmarc/authentication
across the tree finds nothing. Current state:
- A forged From matching a contact's **exact** email still auto-triggers `set_opt_out`
  (→ `do_not_contact`, permanently blocks outreach) and `set_visit_when_nearby` with no
  human in the loop. The exact-match gate only stops *domain-fallback* abuse.
- `_is_bounce` still classifies bounces purely from spoofable From/Subject regexes
  (`graph.py:30-41`); a forged "Undelivered Mail" message whose body contains a target
  lead's address flips that contact to `bad_email`. The recommended DSN check
  (`Content-Type: multipart/report; report-type=delivery-status`) was not added.
**Impact:** sabotage/denial-of-relationship against known leads by anyone who can email the
Proton inbox and knows/guesses a lead's address.

### S2 — MEDIUM-LOW (carried over, partial): `fetch_page` redirect targets not re-validated
**Where:** `gcrm/tools/search.py:247`
**What:** `_is_public_http_url` validates only the *initial* URL. The plain-httpx fallback
then uses `follow_redirects=True`, so a public URL that 30x-redirects to
`http://127.0.0.1:8000/...` or another internal address is fetched anyway. (There is also a
DNS-rebinding TOCTOU — the guard resolves the host, then httpx resolves it again — accepted
as residual risk; the redirect gap is the practical one to close.)
**Impact:** limited on this deployment (VPS/bare-metal, no cloud metadata service), but the
guard's promise is incomplete and the prior review's fix explicitly included redirect
re-validation.

### S3 — MEDIUM (new): auth rate limiter keyed on spoofable `X-Forwarded-For`, and the app port is published on all interfaces
**Where:** `gcrm/api/rate_limit.py:48-53` (`client_key`), `docker-compose.yml` (`ports: "8085:8000"`)
**What:** `client_key` trusts the first `X-Forwarded-For` hop unconditionally. That is
correct *behind* the Apache proxy, but compose publishes port 8085 on `0.0.0.0`, so anyone
who can reach the VPS on 8085 talks to the app directly and can rotate a fake XFF header on
every request — making the brute-force limiter a no-op on the direct path (it also lets an
attacker *spoof someone else's IP into a lockout*).
**Fix shape:** bind the port to loopback (`"127.0.0.1:8085:8000"`) so only the on-host
proxy can reach it, and/or only honor XFF when `request.client.host` is a trusted proxy
address. Verify the VPS firewall as defense-in-depth.

### S4 — MEDIUM (standards + security): no dependency vulnerability scanning anywhere
**Where:** `.github/` (no `dependabot.yml`), `backend.yml`, `android.yml`
**What:** house standard requires Dependabot from the start plus an audit step in CI so a
newly disclosed CVE fails the pipeline. There is no Dependabot config, no `pip-audit`, no
`npm audit` step. The Python side pins via `uv.lock`, mobile via `package-lock.json`, so
without scanning, vulnerable pins persist silently.

### S5 — ACTION (carried over): confirm the leaked Open Brain token was actually rotated
**Where:** `.gitleaksignore` (its own comment: "The credential should be rotated regardless")
**What:** a real Open Brain API token lives in git history (commits `03f20a0`, `b4106be`).
The scrub commit removed it from HEAD; the ignore file baselines the scanner finding. Nothing
in the repo can prove the token was rotated server-side. Until confirmed, treat the token as
live-and-public. **This is an operator action, not a code change** — rotate it in Open Brain,
update the deployed `.env`, then note the rotation date in the `.gitleaksignore` comment.

### S6 — LOW: break-glass `ADMIN_PASSWORD` still active; its actions are unattributable
**Where:** `gcrm/api/auth.py:18,51`, `.env.example`
**What:** by design "transitional until real accounts exist" — the users UI exists
(`/users`), so if accounts have been created, retire it (unset in deployed `.env`). Sessions
from it carry `user_id: None` / `email: "shared-admin"`, so nothing done under it can be
attributed to a person, and its 30-day mobile tokens are not version-revocable
(`jwt_auth.py:8` — no `uid` → no version check).

### S7 — LOW: MCP server actions bypass user attribution (and can send email)
**Where:** `gcrm/mcp/server.py` — `approval_approve` (sends real email via `send_email`),
`approval_reject`, `manual_drop`, `manual_promote`, `run_research`, `trigger_run`
**What:** the MCP server is stdio-local (whoever can run it already has the box), so this is
not an access-control hole. But its state-changing tools — including actually dispatching
approved outreach email — record no actor at all, violating the audit-log standard's
"AI actions are never attributed to 'system' or left unlogged". Folded into C4 below.

### S8 — INFO: any authenticated role can register a push token
**Where:** `gcrm/api/routers/api_push.py:15` (`require_jwt`, not admin)
**What:** a spectator can register a device for push notifications (`send_push_to_all`
broadcasts to every stored token). Spectators may read approvals anyway, so this is
consistent — noting it so it's a decision, not an accident.

### S9 — INFO (accepted): CORS `allow_origins=["*"]`
**Where:** `gcrm/api/main.py:22-27`. Safe as commented (bearer auth, no cookies cross-origin;
session cookie is `SameSite=lax`). No action.

## 3. Coding-standards gaps

### C1 — CI has no lint tier at all
Standard: "lint + typecheck + tests from the first push." Backend CI runs pytest only — no
ruff, no formatter check, and `pyproject.toml` has no lint config. Mobile CI runs
`tsc --noEmit` + jest but no eslint. Also: `backend.yml` triggers only on push to `main`
(path-filtered) — PRs merge without the backend test gate (the refactor PRs #12–#20 relied
on post-merge runs).

### C2 — no integration tier against a real database; migrations first touch real Postgres in prod
Standard (explicit): "Migrations and repository code run against the real database engine in
CI from the first migration (service container)." `tests/conftest.py` states *all DB calls
are mocked*. The 29 migrations in `gcrm/db/migrations/` are executed for real only by the
deploy step (`backend.yml` → `scripts/migrate.py` on the VPS). Two schema bugs already
shipped this way (`026_drop_contacts_status_check.sql`, `027_city_scans_levels_to_10.sql`
are both fix-forward migrations for constraints that misbehaved in prod).

### C3 — no e2e tier
Standard: unit + integration + e2e. Unit coverage is genuinely good (18 backend test files,
per-agent test suites, mobile jest). There is no e2e for the main flows (login → approve →
email-send with `EMAIL_ENABLED=false`; mobile capture → confirm → contact).

### C4 — no correlation IDs; audit trail has no actor
Standard: every unit of work carries a correlation ID; every state-changing action is
audit-logged with actor/action/target/outcome, AI actions included.
- **Correlation:** agent runs have `run_id` (good), but web/mobile requests have no request
  ID, and nothing propagates across the request → queue → agent → email chain.
- **Actor:** `log_interaction` (`db.py:450`) has no actor parameter. Web approve/reject know
  the logged-in user (`request.session["email"]`) but don't record it; mobile approve knows
  only the role; MCP tools record nothing. Today you cannot answer "who approved this
  email?" — admins are indistinguishable from each other, from break-glass, and from AI.

### C5 — function/component size limits
- 45 functions exceed the 40-line limit. Top offenders are the five agent factory closures:
  `create_followup_agent` **349**, `create_research_agent` **259**, `create_scout_agent`
  **197**, `create_enrichment_agent` **171**, `create_outreach_agent` **154** lines. (The
  supervisor got this exact treatment in PR #13 — lift nested node bodies to module level;
  the agents never did.) Next tier: `extract_contacts` 106, `interview_contact` 90,
  `run_blocked_report.main` 84, `google_maps_search` 82.
- Components over the 200-line limit: `research.tsx` **392**, `recon.tsx` **208**.
- Files are all within the 1000-line limit; `gcrm/tools/db.py` (600) is a multi-purpose
  grab-bag mid-split into `db_*.py` modules — finish the split.

### C6 — auth feature set vs. the house standard
The standard requires (any app with accounts): reset-password + create-account links on the
login screen, a settings page (change email/password), two-step delete-account with cascade,
data export, opt-in 2FA. engcrm has: admin-managed accounts (`/users`: add, admin-reset
password, activate/deactivate) and none of the self-service features.

**Honest pushback:** for a 1–2 person internal tool with admin-provisioned accounts, email
self-signup and delete-my-account are arguably *wrong* features, and 2FA/data-export are
low-value. The genuinely missing piece is a **self-service "change my password" page** —
right now a non-admin user cannot change their own password at all, and password changes by
the admin are visible in plaintext in the form. Recommend: build the settings page
(change own password, invalidates `token_version`); consciously waive the rest for this
project and note the waiver here. Flag for Chris to confirm.

### C7 — accessibility not checked
Standard: semantic HTML, keyboard operability, labeled inputs, WCAG AA — "checked
automatically in CI where feasible." The web templates were not audited here and no
automated a11y check exists. Low priority for an internal tool; noted for completeness.

### Phase 1 — security hardening (highest value first)

**T1.1 — Bind the app port to loopback + stop trusting spoofed XFF.**
- `docker-compose.yml`: `ports: "8085:8000"` → `"127.0.0.1:8085:8000"` (the Apache reverse
  proxy is on the same host). Add a comment saying why.
- `gcrm/api/rate_limit.py` `client_key()`: only honor `X-Forwarded-For` when the immediate
  peer (`request.client.host`) is a trusted proxy. Read trusted proxies from a new config
  value `TRUSTED_PROXY_IPS` (comma-separated, default `"127.0.0.1,::1"`) in `gcrm/config.py`,
  with a docstring comment in the existing style. Otherwise fall back to the socket peer.
- Tests: extend `tests/test_rate_limit.py` — (a) XFF from an untrusted peer is ignored
  (key = socket ip), (b) XFF from a trusted peer is honored, (c) default still works with no
  XFF.
- **Operator note (not for Sonnet):** after deploy, confirm Apache proxies to
  `127.0.0.1:8085` and that the VPS firewall doesn't expose 8085.

**T1.2 — Re-validate redirects in `fetch_page`.**
`gcrm/tools/search.py`, plain-httpx fallback (line ~247): set `follow_redirects=False` and
follow redirects manually in a small loop (max 5 hops), calling `_is_public_http_url()` on
every `Location` target before requesting it; refuse (return `""` with the existing
`logger.warning` pattern) when a hop fails validation. Keep total behavior identical for
non-redirecting public sites. The Bright Data branch needs no change (fixed API host).
Tests: extend `tests/test_ssrf_guard.py` with a mocked 302 public→private chain (assert
refused) and public→public chain (assert followed, body returned).

**T1.3 — Gate autonomous inbound-email actions on sender authenticity.**
This is the substantive one; keep the shape minimal and behavior-preserving for legitimate
mail.
- `gcrm/tools/email.py` `_parse_message`: also extract the `Authentication-Results` header
  (may be absent). Add `authenticated: bool` to the returned dict: `True` only if the header
  reports `spf=pass` **or** `dkim=pass` for the From domain (simple substring parse is
  acceptable; document the limitation in the docstring). Absent header → `False`.
- `agents/gcrm-followup-agent/gcrm_followup_agent/graph.py`:
  - `_apply_auto_actions`: require `msg.get("authenticated")` in addition to
    `_is_exact_match(contact)` before calling `set_opt_out` / `set_visit_when_nearby`. When
    skipped for auth, annotate `entry["auto_action_skipped"]` with a
    `"needs human review (unauthenticated sender)"` reason — mirroring the existing
    domain-match wording. Classification, interaction logging, and reply drafting (which is
    already human-approval-gated) proceed unchanged.
  - `_is_bounce` / `_handle_bounce_message`: only auto-`mark_bad_email` when the message is
    a genuine DSN — `content_type` starts with `multipart/report` (extract content type in
    `_parse_message`) — otherwise log/classify but do not mutate the contact.
- The message dict flows through the protocol `InboxFetcher`; update the followup agent's
  test fakes (`tests/test_graph.py` `make_tools`) accordingly.
- Tests: (a) authenticated + exact match → opt-out applied; (b) unauthenticated → skipped
  with annotation; (c) forged bounce (regex-matching subject, non-DSN content type) → no
  `mark_bad_email`; (d) real DSN → `mark_bad_email`.
- Note: messages the classifier skips this way still appear in the web inbox for manual
  classification (`api_inbox.classify`), so nothing is silently dropped.

### Phase 3 — traceability (correlation IDs + audit actor)

**T3.1 — Audit log with actor.**
- New migration `030_audit_log.sql`: append-only table `audit_log(id, at timestamptz default
  now(), actor text not null, actor_type text not null check (actor_type in
  ('user','ai','system-job','mcp')), action text not null, target text, outcome text,
  correlation_id text)`. No updates/deletes ever.
- New `gcrm/tools/db_audit.py` with `log_audit(actor, actor_type, action, target, outcome,
  correlation_id=None)` — own try/except + `logger.warning` on failure so audit writes never
  break the action itself (anti-fragility rule).
- Call it from every state-changing handler with the real actor:
  web routers (`request.session.get("email") or "shared-admin"`), mobile routers (extend
  `require_jwt`/`require_jwt_admin` to return the payload so handlers can use
  `uid`/`sub` — keep the existing `-> str` role-returning signature working by adding a
  parallel dependency, e.g. `require_jwt_payload`, to avoid touching every read endpoint),
  MCP tools (`actor="mcp-client", actor_type="mcp"`), and agent runs
  (`actor=f"agent:{name}", actor_type="ai"`, correlation_id=`run_id`).
- Priority order if trimming: email sends, approve/reject, contact edit/delete, opt-out /
  bad_email auto-actions, user management.
- Tests: unit (mock cursor, assert insert), integration (T2.2 DB): approve flow writes an
  audit row with the acting user's email.

**T3.2 — Correlation IDs.**
- Add a small ASGI middleware in `gcrm/api/main.py`: read `X-Request-ID` or generate
  `uuid4().hex[:16]`, stash on `request.state.correlation_id`, echo in the response header,
  and bind it into log records (a `logging.Filter` + format update in the API entrypoint,
  matching `gcrm/supervisor/logging_setup.py`'s style).
- Pass it into `log_audit` calls from handlers. Agent-side, keep using `run_id` (string-ify
  as `run:{id}`) — do not re-plumb the agents.
